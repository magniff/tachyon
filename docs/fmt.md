# tachyonc fmt and tachyonc explain

0.13. `tachyonc fmt` gives tachyon source one layout, with no options, so
that no agent or person spends a token or a thought on it, and so that
the tools that write code (`edit`, `fix`, the refactorings) write it the
way it is written. `tachyonc explain CODE` says what a diagnostic code
means and how to fix it.

```
tachyonc fmt [FILE|DIR]... [--check] [--dry-run] [--show]
tachyonc fmt [MODULE] [--root ROOT] [--check] [--dry-run] [--show]
tachyonc fmt --all [--check] [--dry-run]
tachyonc explain [CODE|TOOL|--list]
```

## fmt

The files are given as paths (a `.tach` file, a directory: its `.tach`
files, recursively), or as a MODULE of the program (its file and its
children's), or as nothing: every file of the program at ROOT (found as
for query). `--all` is every `.tach` file under `compiler/`, `tests/`,
`examples/` and `bench/` of the current directory: the tree, but the
programs of the tools' transcript tests (`tests/query/`,
`tests/refactor/`), whose text is what they test (untidy imports for
`fix`, a layout for `fmt`).

They are written as one edit of the edit engine ([refactor.md](refactor.md)):
journaled (`tachyonc undo` takes it back), `--dry-run` prints the diff
instead, `--show` the changed lines after. Nothing is checked but the
tokens (below): formatting changes blanks only.

```
$ tachyonc fmt
formatted→2 files→+18 -13 lines
$ tachyonc fmt
note fmt.none: 2 files formatted already
```

`--check` writes nothing: it prints the files that are not formatted, one
per line, then `error fmt.unformatted: N of M files are not formatted` and
`try:` lines (exit 1); exit 0 when all are. tests/run.sh runs
`fmt --all --check` (tests/fmt/run.sh): the tree is formatted.

**Formatting changes no program.** A formatted text is read again and
must have the same tokens and comments as the original, byte for byte (a
comment's trailing blanks aside); else the file is left as it is
(`fmt.unreadable`, "a bug of fmt"). A file that does not lex, whose
brackets do not balance, or with merge conflict markers (`<<<<<<<` at a
line's start), is left as it is too (`fmt.unreadable` for the one
file given; `note fmt.skipped` with the first, for several): the test cases
of syntax errors. A file starting `// Generated by` is its generator's
(compiler/src/front/stdsrc.tach, from compiler/std/embed.sh).

tests/fmt/run.sh proves it on the tree: a copy of every file with its
indentation removed is formatted back to the same bytes (compiler/src and
compiler/std all of them: the fixpoint), every program of the corpus
compiles from the copy to the same assembly and messages (positions
aside), and the compiler built from the copy is the same object, so
`same-output` finds it identical.

### The layout

Line breaks are the source's: lines are never joined (but see
wrapping), so a short `if` stays on its line and a list stays as wrapped.
Within that:

- **Indentation**: four spaces a level. A line in brackets is one level
  deeper than the bracket's line; a closing bracket at the start of a line
  is at its opening line's level. A `{` opened on a line that continues a
  statement opens at the statement's level (the body of `if a\n    && b {`
  is one level in). A line that continues a statement (the line before
  does not end with `;`, `,`, a brace or an opening bracket, or an
  attribute) is one level deeper than the statement's first line; an
  `else` continues an expression, but is at the level of an `if`
  statement. A comment line is at the level of the line after it (inside
  a block before its `}`).
- **Spaces**: one around binary operators, `=`, `->`, `=>` and after `,`,
  `;` and `:`; none inside brackets, around `.`, `::`, `..` and after a
  prefix `-`, `!`, `*`, `&`; none before a call's or an index's bracket; one
  inside braces (`{ x: 1 }`) but a `use` list's (`use a::{b, c};`); one
  before a trailing comment. `<` and `>` are tight in type arguments
  (`Vec<i64>`, `max::<u8>(x)`: after a type's name, `::`, `impl`, or the
  name an item declares, and written tight) and spaced as comparisons.
  (0.14) None inside a closure's bars: `|x, y| x + y`, `||`,
  `move |x| -> i64 { x }`, `|(a, b): (i64, i64)|`; a bar opens a closure
  where an operand starts (after `(`, `,`, `=`, `move`, `return`...), and
  `a | b`, `a || b` after an operand stay operators, spaced.
  (0.15) An f-string's text is never touched; its holes are laid out as
  expressions, with no space inside the braces or before a spec
  (`f"{a + b:>8} {p:?}"`). `x?` is tight; a named argument and a field
  are `name: value`, a default `x: i64 = 1`; `#[derive(Eq, Ord)]` as a
  call's arguments; closers of nested type arguments stay together
  (`Conv<Vec<i64>>>`).
  (0.16) Effect attributes as calls: `#[effects(alloc(Gpa, extern),
  panic)]`, `#[pure] #[no_alloc]` (attributes on one line stay on one,
  a space between them); a bound `F: Fn(i64) -> i64 + effects(panic)`;
  a default type parameter `struct Pair<T, U = i64>`. Inside type
  arguments every `<` after a type's name opens more (`U = Vec< T >` is
  `U = Vec<T>`).
- **Blank lines**: at most one in a row; none at the start of the file,
  after an opening bracket or before a closing one; one between two items
  of a file, impl, trait, module or extern block when either is a
  function, type, impl, trait or block of several lines (one-line items,
  `use`, `mod`, `const`, stay together).
- **`use` lines**: each run of `use` items on consecutive lines (no blank
  line or comment between or after them) as `fix --only tidy-imports`
  writes a module's: the items of one path merged, the names sorted, one
  line when it fits in 100 columns, else wrapped; the run sorted by path,
  segment by segment.
- **Wrapping at 100 columns**: a longer line is broken where it
  overflows, in the brackets around that point, at the first of: a `,` or
  `;` (filled: as many as fit on each line), an `else`, a binary operator,
  loosest first (`||`, `&&`, comparisons, `|`, `^`, `&`, shifts; not
  `+ -` and `* / %`, which 0.13 leaves as they are), (0.14) before each
  `.` of a chain of two method calls or more (`xs`, then `.iter()`,
  `.map(|x| x * 3)`, `.sum()` a line each, one level in), shallowest
  bracket first; else after the `(` or `[` that holds it. A closure's bars
  and the commas between them are no breaks: a long closure with a block
  body has the block's contents on lines of their own. Within a `{ }` opened on the line its contents go on lines of their
  own (a `match`: an arm a line). The lines after it that continue it the
  same way (more arguments, more `&&`) are joined to it first and filled
  again. A line with a token too long for any line (a long string) is left
  as it is. (0.15) No line is broken inside an f-string: a long one goes
  on a line of its own, whole (after its call's `(`). (0.16) Type
  arguments and parameters count as a bracket level: a long `fn f<F: ...,
  G: ...>(a: A, b: B)` breaks its parameter list first; broken inside
  the `<..>`, after a `,`, the next line is one level in.

### Edits are formatted

The edit engine lays out the lines every edit writes (`edit`, `fix`,
`rewrite`, the refactorings): the lines the replaced text spans, in the
context of the whole file, and the `use` runs they touch, nothing else.
So an `edit replace` with text written any way lands formatted, an
import `fix` adds lands in its place in the sorted run, and `rename`
that makes a line too long wraps it.

## explain

```
$ tachyonc explain fmt.unformatted
fmt.unformatted: error, exit 1
`fmt --check`: the files listed (one per line, on stdout) are not formatted.
fix: Run fmt on them (the `try:` line); --dry-run shows the change first.
example:
    compiler/src/x.tach
    error fmt.unformatted: 1 of 178 files is not formatted
    try: tachyonc fmt --dry-run compiler/src/x.tach
```

CODE is any code a tool prints (`query.no-match`, `edit.breaks`,
`refactor.clash`, ...) or the kind of a compiler error or warning
(`type error`, `parser error`, `unsafe`, ...; `type-error` and
`error[type error]` are taken too). A tool's name (`explain fmt`) lists its
codes; `explain` lists every code with its severity, `explain --list` the
codes alone. An unknown code: `error explain.unknown` and `try:` the
nearest codes.

The entries are one table in the source (compiler/src/tools/explain/,
`tools_table` and `refactor_table`); tests/refactor/run.sh checks that
every code the compiler's source prints has one, and that every entry is
such a code.

## Diagnostics

| code | severity | exit | when | try |
|---|---|---|---|---|
| `fmt.unformatted` | error | 1 | `--check`: files not formatted (listed) | `fmt --dry-run FILE`, `fmt FILE` |
| `fmt.none` | note | 0 | nothing to format | |
| `fmt.unreadable` | error | 1 | the one FILE does not lex, its brackets do not balance (or fmt would change its tokens) | |
| `fmt.skipped` | note | 0 | files left as they are, for those reasons (the first named) | |
| `fmt.no-file` | error | 1 | a FILE or DIR is not there, or has no .tach file | |
| `fmt.bad-in` | error | 1 | MODULE names no module of the program | `fmt` |
| `fmt.usage` | error | 2 | an unknown option, several MODULEs, paths and a MODULE | `fmt --check --all` |
| `explain.unknown` | error | 1 | no such code | the nearest codes |
| `explain.usage` | error | 2 | an option, several CODEs | |
