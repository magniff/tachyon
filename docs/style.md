# The vole style (0.25.1)

There is one way to lay out vole source, and `volec fmt` writes it. It
has no options. `volec fmt --all --check` is part of the test suite and
the gate, so the tree is always in this style. The edits of the tools
(`edit`, `fix`, the refactorings) write their lines in it too. The
mechanics are in [fmt.md](fmt.md).

| rule | the style |
|---|---|
| imports | `use` items merged by path, names sorted; in groups: `std`, then `crate`, then the rest (`super`, `self`, child modules), a blank line between two groups; one run across blank lines (a comment ends it) |
| indentation | four spaces a level; a continued statement is one level in |
| width | 100 columns; a longer line is broken at its loosest point: after `,`/`;`, before `else`, a binary operator (loosest first), a method chain's `.`, after a `(`/`[`, inside a `{ }`. This covers calls, signatures, struct literals and `requires`/`ensures` clauses alike |
| spaces | around binary operators, `=`, `->`, `=>`; after `,`, `;`, `:` (`name: Type`); none inside `()`/`[]`, one inside `{ x }`; `Vec<i64>` tight |
| blank lines | at most one in a row; none at the start of a file or block, or before a `}`; one between two items when either spans several lines (one-line items, `use`, `mod`, `const` stay together) |
| braces | on the line of what they open |
| trailing commas | a list whose closing bracket starts a line has one after its last element (a call of one argument too); a list closed on its last element's line has none (`(x,)`, a tuple of one, keeps its comma). No comma after a `}` element in braces (a block, an arm's), `..`, `...` |
| comments | kept byte for byte, inline ones too; a comment line is indented with the line after it |
| file end | no trailing blanks; exactly one newline at the end |
| line breaks | the author's: lines are never joined, only broken (and refilled where wrapping continues a list) |

Formatting never changes a program: fmt checks that the formatted text
has the same tokens and comments as the original (trailing commas
aside), or leaves the file as it is. It is idempotent: `fmt` on
formatted text changes nothing. tests/fmt/run.sh proves both over the
tree, compiling every program of the corpus from a reformatted copy to
the same assembly.

## What is not formatted

`fmt --all` covers `compiler/`, `tests/`, `examples/`, `bench/` and
`tools/`. It leaves out:

- `tests/query/`, `tests/refactor/`: the transcript tests' programs,
  whose layout is what they test (`fmt` on untidy code);
- files that do not lex or whose brackets do not balance (the `err_*`
  tests of syntax errors; `note fmt.skipped` names them);
- generated files (`// Generated by` on the first line:
  compiler/src/front/stdsrc.vl, which compiler/std/embed.sh writes from
  the formatted std);
- `editors/vscode/test/samples/`: the grammar tests, whose `^^^`
  comments point at columns;
- the book's code blocks (book/*.md): fmt reads `.vl` files, not
  Markdown fences. Chapter 18's program is formatted by hand, because
  its session runs `fmt --check`.

## For tools

`crate::tools::fmt::format_source(text) -> i64` formats a whole text in
the process (the language server's format-on-save). It returns a buffer,
or -1 when the text is formatted already or cannot be formatted.
`format_ranges(text, ranges)` formats only the lines an edit wrote.
