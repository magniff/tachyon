# 0.17 eval iterations

Small, focused reruns after the 0.17 validation round
([tests/agent-eval/plans/0.17-validation.md](../../tests/agent-eval/plans/0.17-validation.md)):
one hypothesis each, a few cells, against the 0.16 baseline (`bare`,
`both`, `rust`; `.claude/briefs/evalruns/0.16/`) and the validation's
`guide-core` cells (`.claude/briefs/evalruns/0.17-validation/0.17v-A-*`).
Results are kept under `.claude/briefs/evalruns/iter/NAME/` of the main
checkout. The measure is **cost x Rust**: a cell's median `cost_usd`
over the Rust cell's median for the same task and model (the 0.16
baseline's `rust`, 3 reps), with the geometric mean over the tasks
(`.claude/briefs/evalruns/iter/costx.py`; `run.py compare` for tokens and
the paired test). Next to it, every report gives the **tier-free cost x
Rust** (Haiku 5.5 bills a whole request at 5x when its prompt is over
100k tokens; the tier-free cost re-prices those requests at base rate, as
`.claude/briefs/research/haiku-15.md` fitted, to within 4% of the reported
cost; Sonnet 5.5 has no such tier, so its two costs are equal), the
median **peak context** (the largest prompt of a run's requests) and the
median number of **requests over 100k tokens**
(`.claude/briefs/evalruns/iter/ctxcost.py`). Hosted models only (Sonnet, Haiku), 3 reps per new
cell; a difference inside the baseline cell's range is noise.

## Iteration 1: a mini core and "read the code first"

**Hypothesis.** The up-front guide is overhead on tasks that come with
code (the code already shows the language), while the 1.7k-token core
pays off on from-scratch tasks. Validation, Sonnet, cost x Rust:
`guide-core` 1.95/1.83/1.44 on 01/03/06 against `both` 3.10/2.85/2.76,
but 1.24/1.49/1.20/1.57/1.20 on 07/08/10/16/17 against `bare`
1.22/1.26/0.99/1.18/1.01. A much smaller always-loaded core plus "read
the code first; look up only what the code does not show" should keep
most of the from-scratch gain without the existing-code loss.

**Change.** Two prompt fragments and the conditions that use them
(tests/agent-eval/lib/conds.py):

- `guide-mini` (prompts/guide-mini.md, 340 words, ~600 tokens): one
  compiled example with the main Rust differences as `// Rust:` comments
  (`*T` self, allocators and `new_in(gpa)`, `defer free`, `v.set`/`get`,
  `[u8]` text, `.len` field against `.len()`, `get_or_insert`, `Buf`,
  f-strings, `==` on strings, `read_stdin_in` + `Scanner`), a line of
  further differences, and the lookup lines (`guide --find`, `guide
  TOPIC`, `try`, `check`);
- `+readfirst` (prompts/readfirst.md, 51 words): read the code in the
  directory first and follow its patterns; look a construct up only when
  the code does not show it, and not before it is needed.

**Cells.** `guide-mini+readfirst` and `bare+readfirst` on 01, 03, 06
(write) and 08, 10, 16, 17 (existing code), Sonnet and Haiku, 3 reps
(84 runs).

**Numbers** (2026-10-15, 84 runs, 83 passed; compiler: release-0.17 at
03dbfff; results `iter/01-mini-readfirst/`: `costx.md`, `compare.md`).
Cost x Rust, the geometric mean over the tasks (no run on these tasks
crossed 100k tokens, so the tier-free cost is the same; peak context
16k-50k):

| model | tasks | bare (0.16) | guide-core (0.17v) | guide-mini+readfirst | bare+readfirst |
|---|---|---|---|---|---|
| Sonnet | write 01/03/06 | 3.31 | **1.73** | 1.89 | 2.10 |
| Sonnet | existing 08/10/16/17 | 1.10 | 1.35 | 1.18 | **1.02** |
| Sonnet | all 7 | 1.77 | 1.50 | 1.44 | **1.39** |
| Haiku | write 01/03/06 | 2.78 | 2.38 | **2.35** | 2.48 |
| Haiku | existing 08/10/16/17 | 1.61 | 1.62 | **1.31** | 1.53 |
| Haiku | all 7 | 2.04 | 1.91 | **1.68** | 1.88 |

Per task (cost x Rust, guide-core -> mini+readfirst): Sonnet 01 1.95 ->
2.24, 03 1.83 -> 1.56, 06 1.44 -> 1.91, 08 1.49 -> 1.05, 10 1.20 -> 1.21,
16 1.57 -> 1.27, 17 1.20 -> 1.21; Haiku 01 2.67 -> 2.68, 03 2.31 -> 2.19,
06 2.18 -> 2.20, 08 1.88 -> 1.91, 10 1.94 -> 1.40, 16 1.25 -> 1.26, 17
1.51 -> 0.86. Median turns: Sonnet 11.5 (guide-core) / 9 / 11; Haiku 24 /
26 / 30. Success: 20/21 for Sonnet mini+readfirst (17 rep1 left two tests
timing out), every other cell 21/21. Paired (run.py compare, cost):
mini+readfirst against bare x0.83 Sonnet (p=0.30), x0.85 Haiku (p=0.03);
against guide-core x1.00 / x1.01 (p > 0.5); bare+readfirst against bare
x0.79 Sonnet (p=0.16), x0.96 Haiku. Guide calls per run fall for Sonnet
(guide-core 1.10, bare 1.38 -> 0.43 and 0.48 with readfirst) and stay
about 3 for Haiku; name/API errors per run are unchanged within noise
(Haiku 0.48-0.67, Sonnet 0.71-1.00).

**Verdict.** Partly confirmed. On existing code the read-first line
removes the guide's overhead: Sonnet bare+readfirst 1.02 (bare 1.10,
guide-core 1.35), Haiku mini+readfirst 1.31 (1.62 for both bare and
guide-core). On from-scratch tasks the ~600-token mini keeps Haiku's
whole guide-core gain (2.35 against 2.38) but only part of Sonnet's (1.89
against 1.73; the 1.7k core is still best there). Over the seven tasks,
mini+readfirst is best for Haiku (1.68 against 1.91) and level with
bare+readfirst for Sonnet (1.44 and 1.39 against 1.50). The differences
against guide-core are inside the 3-rep noise except Haiku's 10 and 17.
Next: guide-core + readfirst (the full core, with the instruction to read
existing code first), which should keep Sonnet's write gain. Iteration 3
uses guide-mini+readfirst as its guide condition.

## Iteration 2: familiar names and surface (n2-familiar)

**Hypothesis.** The n2-familiar compiler (edb9f46: a prelude without
`use` for Buf, HashMap, read_line, Scanner, parse_int, trim, split*,
sort, panic, unreachable; `use sibling::X`; `v[i]` and slicing on
Vec/Buf; `p.0` through pointers; `.len()` on slices and arrays; `&mut x`
accepted; better module diagnostics; its guide shows the familiar forms)
removes most name/API errors (36% of agent-caused errors) and so cuts
Haiku's turns and cost on program tasks.

**Change.** None in the harness: condition `guide-core` with that
compiler (`--tachyonc`, copied to `iter/02-familiar/tachyonc`; the 18
tasks pass `check-tasks` with it), against the validation's `guide-core`
(release-0.17 compiler; Haiku 3 reps, Sonnet 10).

**Cells.** Haiku 01-18 x2; Sonnet 01-06 and 15 x2 (50 runs, all passed).

**Numbers** (`iter/02-familiar/`: `costx.md`, `compare.md`). Cost x Rust,
geometric mean over the tasks, old compiler -> familiar:

| model | tasks | cost x Rust | tier-free x Rust | median turns | name/API errors per run | all errors per run |
|---|---|---|---|---|---|---|
| Haiku | 01-18 | 1.89 -> 2.17 | 1.80 -> 1.91 | 27.5 -> 27.5 | 0.41 -> 0.28 | 0.74 -> 0.67 |
| Sonnet | 01-06, 15 | 1.81 -> 1.97 | the same | 7 -> 7 | 0.14 -> 0.14 | 0.50 -> 0.29 |

Error classes per run (distinct errors seen, anatomy), Haiku old ->
familiar: name 0.41 -> 0.28, type 0.20 -> 0.17, syntax 0.11 -> 0.19,
alloc 0.02 -> 0.03; Sonnet: name 0.14 -> 0.14, type 0.16 -> 0.07, unsafe
0.17 -> 0.07, alloc 0.03 -> 0. Paired (run.py compare, median of the
per-task ratios): Haiku input tokens x1.07 (p=0.09), turns x1.00, cost
x1.05 (p=0.08), 9 of 18 tasks inside the baseline's range; Sonnet cost
x1.01 (p=0.30), all 7 tasks inside the baseline's range. Haiku's increase
is three tasks whose sessions grew past 100k tokens: 14 (cost x Rust 1.25
-> 2.40; tier-free 1.64; one run with 10 requests over 100k), 15 (4.04 ->
7.78; tier-free 1.56 -> 2.29; peak 136k -> 172k, 18 -> 34.5 requests over
100k, turns 39 -> 72.5) and 18 (1.49 -> 3.28; tier-free 1.71). Those runs
saw 0-4 compile errors each: what grew was the testing (16: 26 and 2
`./prog` runs against 3-6; 15: 15 and 9 against 7-12) and the output
(15: 117k-139k output tokens against 89k-109k). Haiku gains on the
existing-code tasks 07 (1.74 -> 1.40), 10 (1.94 -> 1.72), 13 (1.89 ->
1.75), 17 (1.51 -> 1.17). Caveat: iteration 3's compiler-task builds
shared the machine for the second half of these runs.

**Verdict.** The error part is confirmed for Haiku (name/API errors -32%)
and the cost part is refuted at this scale. With under one distinct
compile error per run before the change, removing a third of the name
errors saves about 0.1 repair loop per run, which is below the noise of
a 2-rep cell. The cost of Haiku runs is in how long they test and think,
and in whether the session crosses 100k tokens. Keep the familiar forms
for their own sake (fewer errors, smaller guide), but do not expect a
cost win from them. A cost lever for Haiku has to cut the session's
length: the +note and `tachyonc test` cells (iterations 3 and 4) measure
that.

## Iteration 4: the debugging tools (n6-debugtools)

(Iteration 3's own cells are still running; its entry follows when they
finish. Iteration 4 uses only its control cells, already done.)

**Hypothesis.** On bug tasks the tools conditions cost more than plain
(the validation: +15% Sonnet, +44% Haiku on 23-fix-checker). n6-debugtools
(cbbf8c0, on night-017) adds `--trace` failure traces, `tachyonc test`
with crash and timeout locations and `new`/`failing too` labels against
`target/tools/tachyonc`, `tachyonc probe`, `tachyonc reduce`, `guide
debug`, and a hook fix: a test program outside compiler/ is checked with
`target/tachyonc` when it is newer than `target/tools/tachyonc`, so the
hook stops repeating the starter's bug after the agent rebuilt the fixed
compiler. Those should close or flip the gap.

**Change.** Branch n5-iter4 (cbbf8c0 + the iteration harness): compiler
tasks based on cbbf8c0; prompts/tools-core.md gets the row AGENTS.md got
on the branch (`guide debug`, `test` traces, `probe`, `reduce`). The
control is the same cells on night-017 (8564b31, iteration 3's harness and
hooks), so the tools, that row and the hook fix are the only difference.

**Cells.** Sonnet and Haiku, 3 reps: 23-fix-checker
`compiler-tools-core+hook+test` against `compiler-plain`; 07-fix-bugs and
17-debug-crash `tools-core+hook` against `bare` (48 runs, and 48 on
night-017).

**Numbers** (`iter/04-debugtools/`, controls in `iter/03-night017/`). No
run of these cells went over 100k tokens (peaks 19k-63k), so the
tier-free cost equals the cost. 23 is a compiler task (no Rust twin):
median cost and the tools/plain ratio.

| model | task | cells | night-017: tools / plain | debug tools: tools / plain |
|---|---|---|---|---|
| Haiku | 23 | cost | $0.037 / $0.029 = **1.28** | $0.025 / $0.024 = **1.04** |
| Haiku | 23 | turns | 64 / 37 | 37 / 36 |
| Sonnet | 23 | cost | $0.116 / $0.111 = 1.05 | $0.115 / $0.113 = 1.02 |
| Sonnet | 23 | turns | 9 / 10 | 7 / 8 |

| model | task | night-017 tools+hook / bare (cost x Rust) | debug tools tools+hook / bare |
|---|---|---|---|
| Haiku | 07 | 1.52 / 1.63 (turns 24 / 34) | 1.34 / 1.36 (24 / 31) |
| Haiku | 17 | 1.28 / 1.48 (34 / 43) | 1.36 / 1.61 (35 / 49) |
| Sonnet | 07 | 0.98 / 1.34 (7 / 17) | 1.06 / 1.08 (8 / 12) |
| Sonnet | 17 | 1.11 / 1.22 (12 / 19), 2/3 passed | 1.03 / 1.20 (9 / 16) |

Success: every cell 3/3 but Sonnet tools-core+hook on 17 at night-017
(2/3). On 07 and 17 the tools condition was already cheaper than bare on
night-017 and stays so (geomean: Haiku 1.39 against 1.55, then 1.35
against 1.48; Sonnet 1.04 against 1.28, then 1.04 against 1.14).

Use of the new tools, every transcript of the 48 runs: no `--trace`, no
`probe`, no `reduce`, no `guide debug`. `tachyonc test` was run in one of
three Haiku 23 runs (6 calls) and showed a baseline label once (`failing
too` and `new`); Sonnet's 23 runs used `tests/run.sh` (3-6 calls), as on
night-017. Phantom errors (the hook reporting the starter's `'_' is not
covered` on a test file after the agent built its fixed compiler): on
night-017, Haiku tools runs got it at least twice after the build
(`tests/run/match_int_ranges_full.tach` in rep1 and rep2) among 15
reports of the bug's message on test and probe files; with the fix, none
after a build (one on a scratch repro before the agent's first build,
which is a true error then). The remaining check-hook errors on test
files are the agents' own `err_*` cases, which are meant to fail.

**Verdict.** The gap on 23 closes: Haiku's tools/plain goes from 1.28 to
1.04 and its turns from 64 to 37, Sonnet from 1.05 to 1.02. The cause is
the hook fix, not the debugging tools: no agent used `--trace`, `probe`,
`reduce` or `guide debug`, and the Haiku turns saved are the ones it
spent on the hook's phantom errors. The debugging tools are not
discovered from one table row on tasks this size (07, 17 and 23 are
solved by reading the code and one test). Keep the hook fix; to measure
the tools, give a task whose failure is not visible from the source
(a crash deep in a call chain, a hang), or name `tachyonc test` and the
trace in the prompt as +test does.
