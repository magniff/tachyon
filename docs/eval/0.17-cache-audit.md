# Prompt-cache audit of the 0.16 baseline (E7)

Experiment E7 of the delivery research
(`.claude/briefs/research/delivery.md`, §2.3 and §3): what the eval's
Claude Code runs wrote to the prompt cache, what they read from it, and
whether the cached prefix ever broke. No new runs; the transcripts of the
0.16 baseline (516 runs: programs, compiler and hook sets, Haiku and
Sonnet 5.5) and the finished runs of the 0.17 validation (193 runs).

## How it was measured

    python3 tests/agent-eval/lib/cacheaudit.py \
        .claude/briefs/evalruns/0.16/0.16-programs-claude-* \
        .claude/briefs/evalruns/0.16/0.16-compiler-claude-* \
        .claude/briefs/evalruns/0.16/0.16-hook-claude-* [--runs] [--json]
    python3 tests/agent-eval/lib/cacheaudit.py --selftest

Per model request (one assistant message id, counted once; subagent lines
apart) the script takes the usage block. A request whose cache read is
smaller than the whole previous prompt is a **break**; otherwise its
creation is **growth** and is attributed to what was appended since the
previous request: the previous assistant message (thinking, text, tool
calls) and each tool result, by the kind of call (guide, query, Read,
shell reads, builds, edits, hooks, permission denials). Request 1's
creation is the **initial prompt**.

Token counts per source are estimates: the transcript has no per-block
counts. Fitted on 7,045 growth requests, text appended to the context
costs 2.35 characters a token (chars/4 under-counts by 1.7x), each tool
result 68 tokens more than its text, and Claude Code's `thinking_tokens`
estimate matches the measured count (fit coefficient 1.01). The estimates
are scaled to each request's measured creation, so the buckets sum to
the measured totals; 1.5k a run (3.7%) had nothing visible to attribute
it to. Thinking text is redacted in the transcript but its blocks stay
in the context and are written to the cache like any other content.

## Headline numbers (0.16 baseline, 516 runs)

- **94.5% of input tokens were read from the cache**, 5.5% written, under
  0.01% fresh. Haiku 95.6%, Sonnet 88.3%.
- **No prefix ever broke**: 0 breaks in 516 runs, and 0 in the 193
  finished 0.17 validation runs. No compaction (the largest prompt was
  203k tokens; both models report a 1M context window), no images, no
  idle gap over the TTL (the longest gap between requests was 574 s), no
  model change. Two requests (of 20,018) wrote more than their visible
  new content: one a 25.6k-token build output (hook set, 14-ast-pass,
  Haiku rep2), one 4.8k tokens with nothing visible (compiler set,
  21-opt-peephole, Haiku rep2). Neither lost the prefix.
- **Creation per run: median 32.5k, mean 40.0k tokens.** Its split
  (mean per run):

  | source | tokens/run | share |
  |---|---|---|
  | initial prompt (request 1) | 13.4k | 34% |
  | the model's own thinking, kept in context | 8.8k | 22% |
  | assistant text and tool calls | 6.3k | 16% |
  | file reads (Read 2.8k, cat/sed/grep 1.6k, Grep/Glob 0.2k) | 4.6k | 11% |
  | `tachyonc guide` output | 1.8k | 4.6% |
  | Edit/Write results | 1.2k | 2.9% |
  | builds and runs | 1.0k | 2.6% |
  | `tachyonc query` and other tool subcommands | 0.6k | 1.4% |
  | permission denials | 0.4k | 1.0% |
  | hook output (blocks, check results) | 0.04k | 0.1% |
  | other shell, background-task notices, unattributed | 1.9k | 4.8% |
  | breaks | 0 | 0% |

- **Every write was at the 1-hour TTL** (`ephemeral_1h_input_tokens`; the
  runs use a subscription), so writes cost 2x base input, not 1.25x.
  `cost_usd` matches exactly: Sonnet 5.5 at $2 fresh, $4 write, $0.10
  read, $10 output per million (read 0.05x); Haiku 5.5 at 2x write, 0.1x
  read, 5x output of its base. **Writes are 48% of Haiku's input cost and
  84% of Sonnet's**, though they are 4.4% and 11.7% of the tokens. At
  the 5-minute rate (1.25x) they would be 36% and 77%.

## What would cut cache writes

Ranked by tokens saved per run; each item with the number it rests on.

1. **The always-loaded guide (done in 0.17).** The inlined guide and tools
   table wrote 20.7k on request 1; guide-core writes 8.6k: 12.1k less per
   run in the guide and both conditions, and 12.1k less read on every
   later request. For a Haiku both run (19 requests) that is 24k
   base-token equivalents of writes and 22k of reads. compiler-tools-core
   saves 3.2k a run against compiler-tools (10.8k to 7.6k).
2. **Fewer requests.** Thinking and assistant output are 15.1k a run (38%
   of creation), and each request adds its own; Haiku with the inlined
   guide made 37 requests and wrote 97k, against 19 and 47k with both.
   No doc text cuts this directly; it is why turns stay the eval's main
   cost metric.
3. **Whole-file reads.** Reads are 4.6k a run, 30–37% of creation in
   compiler-plain against 4–16% with the tools; 80 Read results and 43
   shell reads were over 5k tokens each (1.5k a run together).
   `query show`, `query context --budget` and `Read` with a line range
   write a fraction of that.
4. **Whole-topic guide prints.** Guide output is 1.8k a run (15–25% of
   creation in bare); 46 guide results were over 5k tokens (0.8k a run);
   repeated fetches of one topic are 0.13 a run, 0.4k tokens (0.19 and
   0.6k in 0.17v-A). Pointing at `guide TOPIC#SECTION` and `guide --find`
   (E4) and noting repeats (E5) can save up to about 0.8k a run.
5. **Permission denials.** 1.31 a run, 0.45k tokens (0.87 and 0.29k in
   0.17v): 227 denied Writes and 443 denied Bash lines over 516 runs, each
   answered with a fixed 340-token message and usually a retry. Allowing
   the scratch paths the agents probe in (or naming the allowed ones in
   the prompt) removes most of them.
6. **Hook output: no cap needed.** 0.04k a run in 0.16 and 0.8k a run
   (2–3%) in 0.17v-C. Median sizes: a query-first block 524 characters,
   a check-after-edit output 197 (largest 1,304; the 10,000-character
   cutoff is never near). Halving the block message would save about
   0.25k a run in the compiler conditions.
7. **Breaks: nothing to fix.** 0 in 709 runs. The prediction "breaks only
   at compaction on long Haiku runs" did not even hold that far: with a
   1M window the longest run (203k) never compacted.

Not a token saving but the largest cost item: the runs write at the
1-hour TTL (2x). At 5 minutes (1.25x) writes would cost 37.5% less, about
18% of Haiku's and 31% of Sonnet's input cost; only 12 of 19,502 gaps
between requests were over 5 minutes (longest 574 s), so few breaks would
follow. Whether Claude Code lets a subscription session choose the
5-minute TTL is not verified. Either way, report cost at the TTL the run
used: `cache_creation.ephemeral_1h_input_tokens` is in every usage block.

Follow-up: `analyze_run` gives a `breaks` count and causes per run; it can
become the `cache_breaks` field of result.json §3 proposes.
